## 二、形态决策（本月主题）

### 2.1 路线对比（2026-10-26 修订：exe 转正）

| 路线 | 门槛 | 数据位置 | 成本 | 对简历的贡献 |
|---|---|---|---|---|
| **A. jpackage app-image（选定）** | **双击 exe，不用装任何东西** | 本机 | 低，JDK 自带工具 | **高**：交付工程能力 + 代码复杂度都算分 |
| B. fat jar（降级为中间产物） | 需装 JDK 21 | 本机 | 极低 | 中：只做开发期验证 |
| C. 部署上线（Web 平台） | 打开网页 | 服务器 | 高：服务器 + 账号 + 隐私合规 | 低：复杂度跑到运维，与求职方向不匹配 |

**修订理由**：jar 的前提是"用户装了 JDK"，而这一条几乎排除了所有非开发者的同学。exe 把这条门槛降到 0，且**不增加任何架构成本**——同一份代码、同一条构建链，只是出口不同。原判断"先 jar 后 exe"是多余的中间态，直接做 exe。


### 2.2 为什么这个月不上线（三条理由，都能写进 README）

1. **隐私成本**：综测材料含学号、成绩单、处分记录（个人敏感信息）。上线 = 你成为个人信息处理者，要承担《个人信息保护法》下的合规责任。一个学生做的年度工具，不值得背这个。
2. **频率成本**：一年只用一次。服务器 360 天待机只为 5 天的使用窗口，是纯支出。
3. **价值错配**：上线带来的"工程复杂度"是运维向的（部署、监控、扩容），面试 AI 应用/后端岗问的是**规则引擎怎么抽象、LLM 不确定性怎么隔离、怎么验证正确性**——这些全在代码里，上线一点都加不了分。

### 2.3 exe 怎么做：jpackage 两条出口，别装错工具

`jpackage` 是 JDK 21 自带（无需第三方）。Windows 上产出两种，**选错要多装一套工具**：

| 产物 | 参数 | 额外依赖 | 用户体验 |
|---|---|---|---|
| **app-image（选这个）** | `--type app-image` | **无** | 一个文件夹，内含 `assessment.exe` + `runtime/`；双击即跑、免安装、免管理员 |
| installer（暂不做） | `--type exe` / `msi` | **WiX Toolset 3.14**（只认 3.x，装 4/5 会失败） | 有安装向导、开始菜单、卸载项 |

关键事实：**本机没有 WiX 也能出真正的 exe**。app-image 里的 `assessment.exe` 就是 Windows 可执行文件，只是"免安装"而非"带向导"。做安装包体验是包装问题，不是功能问题，等真的有人用再说。

体积账（M0 完成后回填实测值）：

| 组成 | 体积 | 说明 |
|---|---|---|
| fat jar（web + POI + Jackson + SnakeYAML） | 45–60 MB | 自己的业务代码不到 1 MB |
| JRE 21 完整 | ≈ 165 MB | 不裁剪，启动最稳 |
| JRE 21 jlink 裁剪（6 模块） | ≈ 45–55 MB | `java.base, java.desktop, java.logging, java.naming, java.net.http, jdk.crypto.ec` |
| **合计（裁剪后）** | **≈ 100–115 MB** | zip 分发，微信能直接传 |

建议顺序：**先不裁 JRE**（210 MB 版本），Spring Boot 对 jlink 裁剪非常敏感，缺模块的报错（`ClassNotFoundException: javax.xml...`）极难查，别在 M0 阶段碰它。M2 再压到 100 MB。

可直接用的命令（Boot 的 loader 类名一定要照抄 MANIFEST，不要凭记忆）：

```bash
# 1) 先看 Spring Boot 打出来的 jar 里 Main-Class 到底是什么
unzip -p target/assessment.jar META-INF/MANIFEST.MF | grep Main-Class
#   Boot 3.2+ → org.springframework.boot.loader.launch.JarLauncher
#   Boot 3.2- → org.springframework.boot.loader.JarLauncher
#   ********** 把输出原样填进下面的 --main-class **********

# 2) 出免安装目录（不需要 WiX）
jpackage --type app-image \
  --name "综测整理" \
  --input target/  --main-jar assessment.jar \
  --main-class org.springframework.boot.loader.launch.JarLauncher \
  --icon src/main/resources/app.ico \
  --app-version 0.1.0 \
  --dest dist/

# 3) 产物：dist/综测整理/综测整理.exe + runtime/
```

`--input target/` 要求该目录里**不要混入其他 jar**（jpackage 会全部塞进去）；先 `mvn clean package` 再清掉 `target/classes`、`target/test-classes` 更干净。


必须注意的三个坑（都会真实发生）：

| 坑 | 现象 | 对策 |
|---|---|---|
| **杀毒误报** | 无代码签名的自解压 exe 常被 360 / Defender 拦或直接删 | README 写明"被拦选'仍要运行'"；**优先发 zip 目录版**而非 installer（误报率明显低）；代码签名证书一年数千元，不做 |
| **SmartScreen 拦截** | 首次运行弹"Windows 已保护你的电脑 / 未知发布者" | 同上，属无签名必然结果，不能靠代码绕过 |
| **点了没反应** | Spring Boot 冷启动 2–4 秒，期间无窗口 | 加启动 splash（`--java-options -splash:boot.png`），并让 `Desktop.browse` 在容器就绪后才调用 |


### 2.4 一个细节：别用固定端口

固定 8080 在开发机上极可能被占（本机已有类似踩坑记录）。做法：

- 配置 `server.port=0` 让系统分配空闲端口
- 启动后通过 `ApplicationRunner` 读实际端口，调 `java.awt.Desktop.browse()` 自动打开浏览器

用户视角：双击 exe → 等 2 秒 → 浏览器自己弹出界面。**没有命令行、没有端口号、没有 Swagger、没有 Java 字样出现在任何地方。**

### 2.5 打包边界：什么该进 exe，什么不该

结论先写：**OCR 不做；模型权重不进包；进包的只有"调用能力"。**

| 能力 | 是否进分发包 | 判断依据 |
|---|---|---|
| **OCR（本地文字识别）** | **❌ 不做** | 见下 |
| 多模态 LLM 调用（看图出 JSON） | ✅ 进包（含 prompt 与 schema） | 体积 0 增加，只是一个 HTTP 客户端 |
| 本地 VLM 权重（Qwen2.5-VL 等） | ❌ 不进包 | 见下 |
| 规则引擎 / 模板 / 配置 | ✅ 全部进包 | 这是产品的真正内核 |

**为什么 OCR 是错的优先级（三条，任一条都够否掉）**

1. **输入形态不对**。你的材料是拍照证书——已确认有 90° 旋转和桌面背景。传统 OCR 要先生成"纠偏 → 去背景 → 二值化"三段预处理，任何一段调不好，输出就是一堆噪声词。
2. **丢的是结构不是文字**。"广东金融学院计算机学院"这行字只有当它出现在**红头位置、印章旁**时才等于"聘任单位"。OCR 输出的是无坐标的线性文本，恰好丢掉了判断级别最需要的信息。
3. **两段不确定串联**。OCR 错一个字 → LLM 基于错字推断 → 误差累积，而且你无法定位是哪一段错的。多模态模型一步出结构化 JSON，错在哪一眼可见。

体积累加也没必要：Tesseract + chi_sim ≈ 50 MB，还要带 native DLL，jpackage 打包时得额外处理 `java.library.path`，是本可以完全避免的工程负担。

> 如果将来真要做"完全离线版"，正确答案也**不是 OCR，而是本地 VLM**（Qwen2.5-VL-3B / MiniCPM-V）。因为问题从来不是"认字"，是"看懂证书"。

**为什么模型权重不进 exe**

| 问题 | 后果 |
|---|---|
| 4–7 GB GGUF | GitHub Release 单文件限 2 GB，微信/网盘传不动，同学下载即劝退 |
| JNI 调 llama.cpp | 要按平台编 native 库，Windows 还要 VC++ 运行库，一次适配三天 |
| 你的 8 GB 显存 | 跑 7B q4 可以，但同时开 IDE + 浏览器就抢显存，用户体验不可控 |
| 模型迭代 | 换个模型就要重新打包发版，直接摧毁"改配置不改代码"这个核心优势 |

**正解**：exe 里进的是 `Extractor` 这个端口和它的配置项（`provider / base-url / model`），模型待在外部——云端 API，或用户自己装的 Ollama。

```yaml
llm:
  provider: openai-compat        # openai-compat | ollama | dify | fixture
  base-url: https://dashscope.aliyuncs.com/compatible-mode/v1
  model: qwen-vl-max             # ★ 必须是「支持图像输入」的模型，见下表
  api-key: ${LLM_API_KEY}        # 只从 Credential Manager / 环境变量读，绝不写进配置文件
  temperature: 0
```

**模型选型（这一步选错，整个项目第一天就卡住）**

纯文本模型**不能读图**。比如 DeepSeek 旧命名 `deepseek-chat` 曾被直接拿去跑证书，得到"我看不到图片"的报错，然后会怀疑是 prompt 写错了——实际是模型不支持。（2026-10 更新：DeepSeek 现行视觉模型是 `deepseek-flash`，旧名 deepseek-chat 已过时；模型名不写死，任何支持图像输入的模型都可在页面填。）默认值必须显式选视觉模型：

| 候选 | 中文证书版式 | 结构化 JSON 稳定性 | 备注 |
|---|---|---|---|
| deepseek-flash（DeepSeek） | 待探针验证 | 待探针验证 | 当前用户主用；OpenAI 兼容端点直接可用 |
| qwen-vl-max（通义） | 好 | 好 | 备选；OpenAI 兼容端点直接可用 |
| glm-4v / 4.5v（智谱） | 好 | 好 | 备选，价格低 |
| 豆包 vision | 好 | 中 | 备选 |
| qwen2.5-vl:3b（本机 Ollama） | 中 | 中 | 完全离线档，8 GB 显存可跑 |

判据不是"谁最强"，而是**在你的两张真实证书上谁的字段准确率最高**——所以探针要跑的不只是一个模型，是 3 个模型 × 2 张图 = 6 次调用，产出一张对比表。这是"视觉识别"这件事唯一可信的验证方式。


### 2.6 一个必须纠正的说法：「数据不出本机」

**这是当前设计里的逻辑漏洞，面试官一问就崩。**

只要用云端 API 读证书图片，图片就已经发到 DeepSeek / 阿里云的服务器了。此时 README 上写"数据不出本机"是**假话**。可选的三档，必须选一档并如实写：

| 档 | 做法 | 隐私强度 | 代价 |
|---|---|---|---|
| **严格离线** | 本机 Ollama 跑 `qwen2.5-vl:3b` | 真的不出本机 | 需装 Ollama（门槛回来了）、8 GB 显存吃紧、准确率下降 |
| **混合（推荐）** | 默认云端 API，**上传前弹窗告知"将发送 N 张图片到 xxx"**，只发裁剪后的材料区，图片在任务结束后本地删除 | 诚实且够用 | 需要一次告知与清理逻辑 |
| **托管** | 把材料传到你的服务器 | 最弱 | 已否定，见 §2.2 |

推荐表述（可直接放 README 首屏）：

> 本工具不做服务器，你的材料不经过任何第三方中转。只有材料图片会发送到**你自己配置**的模型服务商（默认通义 qwen-vl-max），也可切换为本机 Ollama 实现完全离线。任务结束后本地临时图片自动清除。

**这句话同时是工程要求**：它倒逼你实现"上传前告知 + 任务后清理"，两个都是能写进简历的真实功能，而不是文案。

### 2.7 API Key 的安全设计：先说清"锁死不泄露"能做到什么程度

> **先看这一段，别被下面的表吓到。** 安全措施分两档：
>
> | 档位 | 适用 | 要做的事 | 成本 |
> |---|---|---|---|
> | **A. 现在（MVP / 自用 + 几个同学）** | 当前阶段 | ① 代码里永不写 key，只读环境变量 ② `server.address=127.0.0.1` ③ key 不存 localStorage、不回显完整值 | **10 分钟** |
> | **B. 公开发布前** | 决定发给几十人时 | 加 Credential Manager 存储、日志脱敏、序列化清空、上传前告知 | 半天 |
>
> **现在只做 A 档。** B 档现在做属于提前优化，会拖慢 M0，而且届时需求可能已经变了。

#### 前提：本项目是 BYOK（用户自带 Key）

定义：**你（开发者）不内置任何 Key**，不承担任何调用费用。用户双击 exe 后，在本地网页里填入自己的 Key，程序只在那台机器上用它调模型。

这一条定下来，同时解决四件事：

| 问题 | BYOK 下的答案 |
|---|---|
| 谁付钱 | 用户自己。你不承担、也不经手 |
| 服务商条款 | 各自注册各自付费，不涉及转售或共享 |
| Key 反向提取 | 不存在"从 exe 里抠出内置 Key"这个攻击面 |
| 你的责任 | 不保管别人的凭据——但**代码写砸导致用户的 Key 泄露，是伤害别人**，比自损更该防 |

**但 BYOK 有一个比安全更硬的代价：门槛。**

装软件是"点两下"；配 Key 是"注册 → 实名认证 → 开通模型服务 → 生成 Key → 粘贴"。中间任何一步都可能劝退。**这实际上把用户锁定在"技术型同学"这个圈子里。**

所以诚实结论：**BYOK 让"给普通同学用"这件事基本不成立。** 三条出路：

1. **接受现实**（推荐）：定位为"自用 + 技术型同学"，传播靠配置库 PR，而不是用户数
2. 零配置路径：本地 Ollama 版，不用 Key，但要装 Ollama——门槛只是换了个形状
3. 代付 / 共享 Key：成本、责任、条款风险三涨，不做

问卷 Q9b 就是为了量出这道门槛多高。**在拿到数据前，不要假设"同学会自己配 Key"。**

#### BYOK 下的三条额外要求（比通用安全更重要）

| # | 要求 | 为什么 |
|---|---|---|
| 1 | **Key 校验必须做，且要分类报错** | 用户填完 Key 不会自己验证。不做连通性测试，他会卡在"上传材料没反应"然后卸载 |
| 2 | **Key 不参与任何持久化与导出** | `state.json`、artifacts、导出 zip、日志，四处都要排除 |
| 3 | **A 档三条是硬要求，不是可选项** | 自己的 Key 泄露是自损，用户的 Key 因你代码泄露是伤人 |

**连通性测试的错误分类（直接可以写成代码）**

用户填完 Key 后，立刻发一个最小请求（如 `ping`），按返回码给不同提示：

| HTTP | 真实原因 | 提示文案 |
|---|---|---|
| 401 | Key 错 / 已失效 | "API Key 无效，检查是否复制完整" |
| 404 | **模型名错** 或 base-url 错 | "模型 `xxx` 不存在，或该地址不支持此模型" |
| 402 / 403 | 余额不足 / 未开通 | "账户余额不足或未开通该模型" |
| 429 | 限流 | "请求过于频繁，30 秒后重试" |
| 超时 / 连接失败 | 网络或代理 | "无法连接 `api.xxx.com`，检查网络" |

这张表的价值在于：**401 和 404 在用户眼里长得一样，但原因完全不同。** 混在一起提示，用户会以为 Key 填错了，然后跑去重新注册一个——而真实原因是模型名打错了。这是 BYOK 产品最常见的支持成本来源。

这一节回答"用户在网页里填的 Key 怎么保证不泄露"。**先把威胁模型摆出来，否则方案会做成表演。**

先说一个校准：这份清单里**只有一条是真正的"被攻击"**（本机木马），其余全是"自己疏忽"。而你的程序跑在校园网 NAT 后面、没有账号体系、没有别人的数据可偷——黑客没有理由盯上它。所以下面五条里，值得花时间的是 T1（会真丢钱），T5 直接承认防不住。


#### 威胁模型（按真实发生概率排序）

| # | 威胁 | 现实吗 | 对策 |
|---|---|---|---|
| T1 | **用户的 Key 被你的代码写进某处**（配置文件 / state.json / 日志 / 导出 zip） | **BYOK 下的头号风险**，而且伤害的是别人 | 见上文要求 2：四个出口全部排除 |
| T2 | 同一 WiFi 下的同学访问你的 `localhost:8080` | **校园网里很现实**（宿舍/图书馆同网段） | `server.address=127.0.0.1`，不写这行等于监听所有网卡 |
| T3 | Key 被写进日志或异常堆栈 | **很容易发生**：HTTP 客户端 debug 会打印 `Authorization` 头 | 日志脱敏 + 不给 HTTP 客户端开 debug |
| T4 | Key 随导出 zip / artifacts 传播 | 可能：如果配置快照被写进产物 | 产物只放业务数据，不放配置 |
| T5 | 本机恶意软件读内存或解密 | 可能 | **本地应用无法防御**，见下方"诚实边界" |

#### 四层防护（B 档完整版；A 档现在只需 L3 + L4 的第一条）

| 层 | 做法 | 强度 | 实现要点 |
|---|---|---|---|
| **L1 不落盘** | Key 只存在 Java 进程内存，退出即失效 | 最高 | 每次启动重输；提供"记住我"开关才进 L2 |
| **L2 OS 凭据库** | 存 Windows Credential Manager（底层 DPAPI，绑定当前 Windows 用户） | 高 | Java 用 JNA 调 `CredWriteW / CredReadW`；或 `jkeyring`。**别自己写 AES**——密钥放进 jar 里等于没加密 |
| **L3 前端只写不读** | 网页提交后立刻清空输入框，之后页面只显示后端返回的掩码 `sk-****1a2b` | 高 | **Key 只在后端内存，前端永不持有完整值**。不要存 localStorage（浏览器扩展和中国式"安全软件"都能读） |
| **L4 传输与日志** | 绑 127.0.0.1、`type=password`、日志正则脱敏 | 必做，成本最低 | 见下方三个坑 |

#### 三个必踩的坑（都是具体的一行配置）

**坑 1：默认监听所有网卡。**

```yaml
server:
  address: 127.0.0.1    # ← 不写这行，Spring Boot 监听 0.0.0.0
  port: 0               # 随机端口
```

不写 `address` 时，同一宿舍楼的人打开 `http://你的IP:8080` 就能看到你的界面，能改配置、能看到掩码、能触发用你的 Key 花钱的请求。**这是本项目最可能发生的一次真实泄露，不是理论风险。**

**坑 2：日志把 Bearer Token 原样打出来。**

`RestClient` / `WebClient` / OkHttp 开到 debug 级别，会把请求头连同 `Authorization: Bearer sk-xxxxx` 一起写进 `logs/app.log`。做法：

- 不给 HTTP 客户端开 debug（只给 `com.abing.assessment` 开）
- logback 里对所有日志做全局脱敏，兜住"哪天不小心开了 debug"：
  ```xml
  <pattern>%replace(%msg){'(sk-[A-Za-z0-9_\-]{12,})', 'sk-***MASKED***'}</pattern>
  ```

**坑 3：Key 进了导出的压缩包或 state.json。**

`state.json` 记录任务进度时很自然会把"本次使用的配置"整个序列化进去。规则：**快照只存 `provider/model/base-url`，`api-key` 字段在任何序列化前置空**。

#### 诚实边界（这条写进 README，比吹"军事级加密"值钱）

本地应用的加密本质是"用放在同一台机器上的钥匙，锁这台机器上的箱子"。**如果攻击者已经能以你的 Windows 用户身份运行程序，他也能调用同一个 Credential Manager 拿到明文。** 所以准确的表述是：

> Key 不会因为你的疏忽（提交到 git、共享配置文件、留日志、同网段访问）而泄露；它防不住已经控制你电脑的恶意程序。

面试时能主动说出这个边界，比说"我用了 AES-256 银行级加密"更能证明你懂安全——因为后者恰恰说明你不知道密钥该放哪。

#### 顺带回答"exe + 网页是不是两个东西"

不是，是同一个东西的两个面：

```
综测整理.exe  ──启动──►  内嵌 Spring Boot :随机端口  ──自动打开──►  系统浏览器 localhost
   (jpackage 壳)              (页面与 API 都在这里)                 (用户看到的就是"网页")
```

用户视角是"一个桌面软件 + 一个网页界面"；工程视角只有一份 Spring Boot 应用。**不需要 Electron、不需要前后端分离、不需要 Node**——这也是为什么 exe 路线不会增加架构成本。

> 可选升级（不推荐现在做）：用 JavaFX WebView / JCEF 把浏览器内嵌进窗口，看起来更像"客户端"。代价是 +30~50 MB 体积和一堆渲染兼容问题。M3 之前不要碰。

### 3.1 零数据库方案（D2 的落地）

数据分三类，各有归属，没有一类需要关系型数据库：

| 数据 | 载体 | 理由 |
|---|---|---|
| **规则/目录/模板映射**（学校层 + 学院层） | `configs/**.yaml`，**jar 外部目录** | 要能被别人 PR 修改。打进 jar 里就锁死了，改了就得重新打包 |
| **任务运行态**（当前任务、stage 进度、复核结果） | `artifacts/<task>/state.json` + 各阶段产物文件 | 生命周期 = 一次评测；结束导出 zip 后就没用了 |
| **查表数据**（竞赛目录 ~千条、期刊目录） | YAML 加载 → 内存索引（启动时建一次） | 只读、全量、单机，查询是内存操作，比 SQL 快 |

**唯一需要注意的点**：竞赛名称模糊匹配需要索引。启动时把 `competition` 列表构造成「全称 map + 别名 map + 归一化后的倒排索引」，内存占用约几 MB，可接受。

#### 3.1.1 如果确实要引入 H2：最小 schema 是 4 张表，不是 16 张

**先澄清一个容易记混的点：本项目的建议不是「用 H2」，而是「先不用数据库」。** H2 是"将来真要存历史时才考虑"的选项，不是 MVP 的一部分。

**什么时候才该引入（三个触发条件，满足任一再动）**

| 触发 | 说明 |
|---|---|
| 需要历史任务列表 | "去年算了多少分，今年和去年对比" |
| 需要跨任务统计 | 看哪些字段老抽错，用来改进 prompt |
| 需要材料指纹去重 | 同一张证书重复上传，靠 SHA-256 识别 |

这三条现在都不需要。不满足就引入，等于给自己加一层迁移、备份、版本兼容的负担。

**v1.sql 不能直接拿来用**，两个原因：

1. 它是 MySQL 语法（`ENGINE=InnoDB`、`ON UPDATE CURRENT_TIMESTAMP`、`JSON` 类型），H2 上跑不了，得重写 DDL。
2. **16 张表里有 9 张是"配置表"**（college / rule_version / score_rule / bonus_rule / material_requirement / excel_template / rule_source / competition / competition_alias）。而这些配置已经在 YAML 里了——**同一份数据存两处，是 bug 的温床**：改了 YAML 忘了改库，或者反过来。

**最小 schema（4 张表）**

```sql
-- 1. 一次评测任务
CREATE TABLE task (
  id            VARCHAR(36) PRIMARY KEY,
  college       VARCHAR(64) NOT NULL,
  academic_year VARCHAR(16) NOT NULL,   -- 2025-2026
  rule_version  VARCHAR(32) NOT NULL,   -- 指向 configs 里的版本号，不是外键
  status        VARCHAR(20) NOT NULL,   -- PREPARING/REVIEWING/DONE/FAILED
  created_at    TIMESTAMP   NOT NULL DEFAULT CURRENT_TIMESTAMP,
  finished_at   TIMESTAMP   NULL
);

-- 2. 一份材料
CREATE TABLE material (
  id           VARCHAR(36) PRIMARY KEY,
  task_id      VARCHAR(36) NOT NULL,
  orig_name    VARCHAR(255) NOT NULL,
  archive_name VARCHAR(255) NULL,       -- 材料3：蓝桥杯+国赛一等奖
  sha256       CHAR(64)    NOT NULL,    -- 去重 / 回归集识别
  category     VARCHAR(20) NULL,        -- 德育/智育/体育/美育/劳育
  extract_json CLOB        NULL,        -- 抽取结果原文
  review_state VARCHAR(20) NOT NULL,    -- PENDING/CONFIRMED/REJECTED
  CONSTRAINT fk_mat_task FOREIGN KEY (task_id) REFERENCES task(id)
);

-- 3. 一条得分项（每一分都要能追回依据）
CREATE TABLE score_item (
  id           BIGINT AUTO_INCREMENT PRIMARY KEY,
  task_id      VARCHAR(36)  NOT NULL,
  material_id  VARCHAR(36)  NULL,       -- 职务类无证明，允许为空
  dim          VARCHAR(20)  NOT NULL,
  rule_code    VARCHAR(100) NOT NULL,   -- 对应 YAML 里的规则编号
  item_name    VARCHAR(255) NOT NULL,
  score        DECIMAL(10,2) NOT NULL,
  basis        VARCHAR(500) NULL,       -- 细则条款 + 原文摘录
  review_state VARCHAR(20)  NOT NULL,
  CONSTRAINT fk_si_task FOREIGN KEY (task_id) REFERENCES task(id)
);

-- 4. 一次计算的汇总（结果可重算，所以单独一张，不覆盖历史）
CREATE TABLE task_result (
  id            BIGINT AUTO_INCREMENT PRIMARY KEY,
  task_id       VARCHAR(36) NOT NULL,
  moral         DECIMAL(10,2),
  intellectual  DECIMAL(10,2),
  physical      DECIMAL(10,2),
  aesthetic     DECIMAL(10,2),
  labor         DECIMAL(10,2),
  total         DECIMAL(10,2),
  rule_snapshot CLOB,                   -- 规则快照，绝不含 api-key
  calculated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  CONSTRAINT fk_res_task FOREIGN KEY (task_id) REFERENCES task(id)
);
```

**v1.sql → 4 张表的映射**

| v1.sql | 怎么办 |
|---|---|
| 9 张配置/目录表 | **全部进 YAML**，不进库 |
| `assessment_task` | → `task` |
| `material_item` | → `material` |
| `score_detail` + `score_material_ref` | → `score_item`（一对一合并） |
| `score_calculation` | → `task_result`（改成可重算的多行） |
| `material_operation` | 删（二期） |
| `export_task` | 删（状态并入 `task.status`） |

**H2 的三个坑**

| 坑 | 后果 | 对策 |
|---|---|---|
| **数据库文件放在 exe 安装目录** | Windows 下 `Program Files` 不可写，启动即失败，报 `Read-only database` | 放 `%LOCALAPPDATA%\Assessment\data\`，代码里用 `System.getenv("LOCALAPPDATA")` |
| 用 H2 的 `JSON` 类型 | JDBC 读写要特殊处理，各版本行为不一致 | **用 `CLOB` 存字符串**，应用层用 Jackson |
| H2 大版本升级不兼容旧文件 | 用户去年的数据突然打不开——对一个一年用一次的工具是灾难 | **锁定依赖版本**；若真要长期存档，SQLite 文件格式更稳定 |

```yaml

    url: jdbc:h2:file:${LOCALAPPDATA}/Assessment/data/assessment;AUTO_SERVER=TRUE
    username: sa
    password: ""
    driver-class-name: org.h2.Driver
```

### 4.2 为什么这么分（这套分法就是面试要讲的东西）

| 设计 | 解决的问题 | 可验证的收益 |
|---|---|---|
| `domain` 零框架依赖 | 规则引擎的正确性不该被容器启动拖慢 | 跑一次单测 **< 3 秒**，能放心堆几百个表驱动 case |
| `Extractor` 端口化 | LLM 是不确定源，不能污染确定逻辑 | 单测用 `FixtureExtractor`，**永不联网**，结果可复现 |
| `ExtractedFact` 带 `evidenceQuote` | 防幻觉 + 支撑人工复核 | 每个判定都能追回原文，错判可定位到具体字段 |
| stage 产物落盘 | LLM 调用慢且花钱，不能"改一行就全链路重跑" | 可 `--from-stage=score` 只重算，省时省钱 |
| 配置在 jar 外部 | 细则年更、他校适配 | 改 YAML 不改代码、不重打包 |

### 4.3 Pipeline 与可重入

```
materials/
   │
   ├─[1] ImagePreprocess ──► 01-preprocessed/     （二期；本月可跳过）
   │
   ├─[2] Extract (LLM)  ───► 02-extracted/*.json  （每份材料一个 JSON，含 evidence）

   ├─[3] Classify+Match ───► 03-reviewed/         （候选规则 + 目录匹配 + 未匹配兜底）

   │        └── 人工复核（Web 页面改判，改判留痕）
```

`state.json` 记录每个 stage 的完成时间与产物的 hash。重跑时若输入 hash 未变则跳过。

## 五、规则引擎设计（项目最值钱的部分）

### 5.1 签名：一个纯函数

```java
public final class RuleEngine {
    public ScoreResult evaluate(List<ExtractedFact> facts, RuleConfig config, AcademicYear window);
}
```

无 IO、无 Spring、无随机、无时间依赖（window 是入参不是 `now()`）。**同样的输入永远同样的输出**——这一条决定了它可被穷举测试。

### 5.2 五步处理顺序（顺序错了结果就错）

| 步 | 动作 | 关键点 |
|---|---|---|
| 1 | **窗口校验** | 日期不在评测学年 → 标 `inWindow=false` + 给依据，**不删除**（最终由班委定，见探针文档 6.2） |
| 2 | **查表定级** | 竞赛名 → 目录条目；精确 → 别名 → 归一化模糊 → 返回**候选列表**交人工，绝不猜 |
| 3 | **规则匹配** | fact → 命中的 `bonus_rule`（可能多条 → 全部保留为候选） |
| 4 | **冲突合并** | 按 `conflict_group` 分组：`MAX_ONLY` 取最高 / `NO_ACCUMULATE` 只计一次 / 达 `max_score` 截断 |
| 5 | **维度聚合** | `德育 = 基础×0.3 + 互评×0.2 + 素质加分×0.5 − 扣分`，负值归零 |

### 5.3 三条硬纪律

1. **未匹配绝不静默丢弃**。配置里找不到的加分项 → 进 `UNMATCHED` 列表并在页面高亮「需人工判定」。漏一项就是评奖事故。
2. **每一条得分都必须能回答"凭什么"**：`ruleId` + 细则条款号 + `evidenceQuote` + 来源材料号。答不出来的分数不允许出现在结果里。
3. **同名不同源必须能区分**：`军训先进个人` 既可能是「校级其他各类先进个人 +6」也可能是「校级活动获奖 +8」，引擎给两条候选 + 各自依据，人选。

### 5.4 测试策略（面试可直接讲的数字）

表驱动测试，用已有金标准作基准：

```java
@TestFactory
Stream<DynamicTest> moralGoldenCases() {
    // 聘书(班主任助理, 2025-09-01, 聘期2年) → 德育·学生干部 +10, inWindow=true
    // 军训先进个人(2024-09-24)               → 候选 +6, inWindow=false（不计入但仍列出）
}
```

| 层 | 内容 | 目标用例数 |
|---|---|---|
| 单元 | 冲突合并 / 窗口 / 截断 / 加权归零 | 40+ |
| 契约 | YAML → Java 映射 + schema 校验（故意写错配置要报错） | 10+ |
| 端到端 | 2 份真实证书 → 完整 zip，断言文件树与表格单元格 | 3+ |

### 5.5 生成层的验收标准：官方输出规格（2026-10-26 从 PDF 原文提取）

以下是 `材料2：综测评定注意事项.pdf` 第 3 页原文，**这是生成层唯一的验收标准，不要凭记忆或"常规说法"**。

| 项 | 官方原文 | 落到代码 |
|---|---|---|
| 压缩包名 | "学号＋姓名" | `{studentNo}_{name}.zip` |
| 包内结构 | "五个文件夹+综测评定表" | 6 个顶层条目 |
| **文件夹顺序** | **"德育+智育+美育+体育+劳育"** | ⚠️ **美育在体育前**，与"德智体美劳"的日常说法不同 |
| 文件夹内排序 | "按评定表中填写的顺序排放" | 与加分明细表的行序一致，不是按文件名 |

## 六、LLM 的位置：端口化，Dify 是适配器

### 6.0 先定分工：AI 干什么、不干什么

一条定位，**不能被"简化"掉**：

> **AI 承担"看懂材料"的全部，不承担"算分"。** 前者是人工耗时的绝大部分，后者必须可复现。

| 环节 | 谁做 | 依据信号 |
|---|---|---|
| 识别这是哪种材料（聘书/证书/成绩单…） | **AI** | 版式、标题、印章 |
| 读出姓名 / 单位 / 日期 / 奖项 / 聘期 | **AI** | 文字 + 空间位置 |
| 推测级别（国家/省/校/院） | **AI 给弱判断 + 依据** | 颁发单位 |
| 推测归属维度（德/智/体/美/劳） | **AI 给候选** | 活动性质 |
| 竞赛名 → 目录条目 | 规则引擎（模糊匹配）+ 人从候选里选 | AI 抽出的名称 |
| 分值 | **规则引擎（纯函数）** | 配置矩阵 |
| 归类 / 重命名 / 填表 / 打包 | 代码 | —— |

**AI 覆盖的正好是人工最累的前四项**（问卷 Q4 里"判断能加多少分""查目录定级"的输入全都来自这里）。如果把这四项砍掉，剩下的确实是全人工——那就没有做的必要了。

**为什么"算分"不能交给 AI**（三条，任一条都够）

1. **不可复现**：同一份材料跑两次可能两个答案，用户没法申诉。
2. **不可审计**：说不出"依据哪条细则第几款"，而班委审的恰恰是这个。
3. **不可配置**：细则年更时，改 prompt 的风险比改 YAML 高十倍。

**注意这里的关系**：正因为 AI 的输出被冻结成带 `evidenceQuote` 的事实，人才能"看一眼就确认"。**如果 AI 直接给分数，人就只能"要么信、要么全部重算"——那才是真正没意义的形态。**

**三个必须留给人（AI 做不了或不该做）**

| 场景 | 为什么 | 人的动作 |
|---|---|---|
| 多人材料框出本人姓名 | 要画框标注，不是阅读理解 | 点点鼠标（二期可半自动） |
| 边界歧义（"军训先进个人"算校级荣誉还是校级活动获奖） | 细则本身两可，AI 选哪个都可能错 | AI 给候选 + 依据，一次下拉 |
| 材料里根本没有的信息（纯线上活动是否计分） | 无法从图片推出 | 人勾一个选项 |

这三件事加起来是"确认 30 秒"，不是"从零做 3 小时"。**AI 把工作从"做"降级成"审"，这是产品价值的准确描述。**

### 6.1 三个实现，一个接口

```java
public interface Extractor {
    Extraction extract(MaterialSource source);   // 返回 facts + evidence + confidence
}
```

| 实现 | 场景 | 用途 |
|---|---|---|
| `OpenAiCompatExtractor` | DeepSeek / 通义 / Ollama / vLLM（都兼容 `/v1/chat/completions`） | **生产默认**。换模型只改 `base-url` + `model` |
| `DifyWorkflowExtractor` | Dify 工作流 API | 可选。**验证阶段用，不作为交付形态** |
| `FixtureExtractor` | 读 `02-extracted/*.json` | 单测/离线演示。让测试永不联网 |

配置化选择：
```yaml
llm:
  provider: openai-compat     # openai-compat | dify | fixture
  base-url: https://api.deepseek.com/v1
  model: deepseek-flash       # ★ 仅是预填建议，任何支持图像输入的模型都可填，不写死
  temperature: 0
```

### 6.2 Dify 的正确用法（本月可选动作）

**做**：用 Dify 云端 sandbox 或直接调 API，把「证书图片 → 抽取 JSON」这一段的 prompt 与模型选型跑通，产出物 = **prompt 定稿 + 与金标准的字段对比表**。

**不做**：
- ❌ 不在本机 Docker 起 Dify 全栈。8 容器常驻占 4–6 GB 内存，你这台 16 GB 内存的机器还要跑 IDE 和 Ollama，会互相挤（此前已确认过 14B 模型的判断，同一约束）。
- ❌ 不把 Dify 工作流当交付形态。理由：别人要用你的工具，得先自己部署一套 Dify——与"双击可用"直接冲突。
- ❌ 不让 Dify 参与算分。LLM 平台承载确定性规则是架构倒挂。

**成本对比**：Dify 走一遍 ≈ 半天（拉环境、搭工作流、调节点）；直接写 30 行脚本调 API ≈ 20 分钟，且脚本本身就是将来的 `OpenAiCompatExtractor` 原型。**建议先用脚本，Dify 只在你想看"可视化编排长什么样"时才用。**

## 七、关键设计决策（ADR 速查表）

| ID | 决策 | 理由（一句话） | 代价 |
|---|---|---|---|
| ADR-1 | 模块化单体，单 exe 分发 | 服务数为 1，拆微服务只增加分布式复杂度 | 无 |
| ADR-2 | 领域内核零框架依赖 | 规则正确性的验证速度与可重复性优先 | 需写手工映射（YAML→对象） |
| ADR-3 | 无关系型数据库 | 数据是单次任务的短生命周期中间产物 | 跨任务统计查询不方便（暂不需要） |
| ADR-4 | LLM 只做事实抽取 | 算分必须可解释、可复现、可审计 | 需要一套规则配置 + 人工复核 |
| ADR-5 | 人工复核是一等功能，不是补丁 | 学院制度本身接受"草稿 + 班委纠正" | 多一套 UI 与状态机 |
| ADR-6 | 配置在 exe 外部 | 他校适配靠 PR，不能靠重新打包 | 需处理配置缺失/版本不匹配的兜底 |
| ADR-7 | 端口随机 + 自动开浏览器 | 避免 8080 冲突，用户零参数 | 无 |
| ADR-8 | v1.sql 归档，不实现 | 它是平台形态遗产，与本地单用户定位不符 | 若将来转平台需重做持久层 |
| ADR-9 | **不做 OCR，直接多模态 LLM** | 拍照证书 OCR 需三段预处理且丢失版式信息 | 必须联网；离线诉求只能靠本地 VLM |
| ADR-10 | **jpackage app-image，不做 installer** | 免 WiX、免管理员、免杀毒误报加重 | 无安装向导，靠 zip 分发 |
| ADR-11 | **模型权重不进包，只进调用能力** | 换模型不该重新发版 | 首次使用需配 API Key |
| ADR-12 | **隐私表述如实分档，不写"数据不出本机"** | 用云端 API 时这句话是假的，一问就崩 | 需实现上传前告知 + 任务后清理 |
| ADR-13 | **Key 存 Credential Manager，前端只写不读** | 前端持有 = 浏览器扩展可读；自写 AES 密钥在 jar 里等于没加密 | 需 JNA，多一次 OS 交互 |
| ADR-14 | **默认模型必须是视觉模型；模型名不写死** | 纯文本模型读不了证书，会把"模型不支持"误判成"prompt 写错"；模型阵容会更新（deepseek-chat 已过时 → deepseek-flash），写死=埋雷 | 探针需对比多个模型；页面须允许手填任意模型名 |
| ADR-15 | **BYOK：分发包内不内置任何 Key** | 费用、条款、Key 反向提取三个问题同时消失 | 用户需自备 Key，实际把用户锁定在技术型圈子 |
| ADR-16 | **AI 是主力：承担材料理解，不承担算分** | 砍掉 AI 只剩填表打包，项目失去意义；让 AI 算分则不可复现/审计/配置 | 需 prompt 工程 + 复核 UI |

### 9.1 关于「一个月内把 OCR 和 LLM 都融进去」

拆成四件事看，只有一件该做：

| 事项 | 判断 | 理由 |
|---|---|---|
| LLM 抽取能力进 exe | ✅ 做，11 月 | 只是 `Extractor` 的一个实现类 + 三行配置，工作量在 prompt 调优，不在集成 |
| OCR 进 exe | ❌ 不做 | §2.5 三条理由，且会把 100 MB 抬到 150 MB |
| 模型权重进 exe | ❌ 不做 | 体积 / JNI / 显存三重成本，见 §2.5 |
| 完整闭环（抽取→复核→算分→打包）跑通 | ❌ 不是这个月 | 5 个 stage，每个都要单独调试，12 月底是现实节奏 |

**「融入」的正确粒度**：这个月让 LLM **在脚本里**跑通并给出准确率数字；**下个月它才配进 exe**。顺序反过来，就是在给一个还没验证的环节做工程包装——万一抽取准确率不达标，你包装得越好，返工越贵。

一句话：**本周先让 exe 双击能跑（3 小时的事），LLM 用脚本验证（1 天的事），两件事都不难，但不要合成一件做。**

| **页面填 Key（BYOK）** | ✅ | DPAPI 加密存 `%LOCALAPPDATA%/Assessment/llm.key`，只回显掩码 `sk-ab****wxyz`；**先测后留**（测不通撤销，不留坏 Key）；单测验证磁盘上是密文 |
| 探针实跑 | 🟡 改由页面入口执行 | 见下方「顺序调整」 |

**过程中修掉两个真问题（都会咬人）**

1. **`server.port=0` 在本机不可靠**。Tomcat 拿到随机端口后要关闭探测 socket 再重新 bind，中间那一瞬被 `WorkBuddy.exe` 抢走，报 `Port 50545 was already in use`——这个错误对用户毫无意义。改为在 `main()` 里自己探 `18080-18120`，找到能绑的再通过 `System.setProperty("server.port", ...)` 告诉 Spring。
2. **`WebConfig` 里 CORS 写的是 `allowedOriginPatterns("*")`**。等于让浏览器里任何一个网站都能跨域调用本地接口，包括消耗用户 API Key 的那个。已收窄到 `http://127.0.0.1:*` / `http://localhost:*`。

**一个刻意的设计取舍：`RuleConfig` 故意不强类型化**

只把 `school / college / rule_version / formulas / global_constraints` 抽成 record 字段，德育、智育那些规则明细原样留在 `raw()` 里。

原因：规则 schema（§12 的 S2）还没定稿。现在把 `moral.student_officer.groups[].items[]` 写成一串嵌套 record，等智育的"两次查表"和体育的"公式换算"进来，一定要返工**并且返工两次**。

> **提前强类型化 = 提前把假设写死。** 等 S2 定了再逐步收窄，比反过来便宜得多。

**留给你的只剩一件：跑探针**

`cd probe` → 设 `LLM_API_KEY` → 见 `probe/README.md`。这个数字决定 11 月做什么。

**顺序调整（2026-10-27）：探针从"脚本"搬到"页面"**

原计划是先跑 Python 探针、拿到准确率、再集成模型。实际改成了**边集成边验证**：`/api/extract` 就是应用内的探针。

| 走法 | 优点 | 缺点 |
|---|---|---|
| 先脚本后集成 | 隔离问题（是 prompt 还是代码） | 同一件事做两遍；脚本的结果不能直接复用 |
| **边集成边验证（实际采用）** | 一次到位，验的就是产品本身 | 出问题时要区分"prompt 不行"还是"代码错" |

之所以能这样，是因为错误路径已经先验证干净了（401 / 415 / 400 各归各位），剩下唯一的变量就是"模型看得准不准"。**如果连错误分类都没验证就直接调模型，那才是把两个问题混在一起。**

Python 探针仍然保留：它的价值变成"多模型横向对比"（`probe.py` 一次跑 3 个模型出对比表），这是页面做不到的。

### 9.4 一次真实的翻车记录（2026-10-27）

用户双击 exe 后**完全没反应**。诊断结果：**服务其实启动成功了，而且连点了 8 次起了 8 个实例**，端口从 18080 一路涨到 18085。

| 问题 | 为什么致命 | 修法 |
|---|---|---|
| 启动后不打开浏览器 | 程序没有窗口、没有托盘图标，用户唯一的感知渠道就是浏览器。不开 = "点了没反应" | `ApplicationReadyEvent` 里拿 `local.server.port` → `Desktop.browse`；拿不到桌面会话时用 `rundll32 url.dll,FileProtocolHandler` 兜底 |
| 可以重复启动 | 双击的语义是"打开界面"，不是"再起一个服务"。连点产生多个进程互相抢端口，用户还会以为程序坏了 | 文件锁 `%LOCALAPPDATA%/Assessment/app.lock` + 端口探测：拿不到锁就轮询已有实例（最多 5 秒）并直接打开它 |

> **验收标准因此修正**：M0 的出口不是"进程起来了"，而是"**用户双击之后能看到东西**"。
>
> 这条差点漏掉，因为它不是代码问题而是产品问题——所有自动化测试（HTTP 200、端口监听、日志正常）都通过了，唯独用户看不到任何东西。

### 9.5 单实例与升级打架（2026-10-27 实测踩到）

装好新版本、双击新的 exe，**看到的还是旧界面**。

原因链条：

```
用户 12:05 双击旧 exe → 占了 18080
我 12:07 构建新版本 → 启动 → 单实例检测发现已有实例 → 复用并退出
浏览器打开的是旧实例 → 新接口 /api/llm 返回 404
```

**单实例检测只判断"有没有在跑"，不判断"跑的是哪个版本"。** 结果就是：新版本永远启动不了，而用户完全不知道发生了什么——他只会觉得"新版本没生效"。

修法（待做，见下）：

| 步骤 | 做法 |
|---|---|
| 1 | `/api/status` 已经返回 `version` 字段（现成） |
| 2 | 新实例拿不到锁时，比较自己的版本与已有实例的版本 |
| 3 | 不一致 → 打开旧实例页面（至少让用户看到东西）+ 在页面上显示横幅"检测到旧版本 vX 正在运行，请关闭后重新双击" |
| 4 | 不要自动杀旧进程：日志、正在进行的任务都会丢，用户可能正开着页面 |

> 这个坑的本质：**单实例机制假设"同版本"**，而升级恰恰打破这个假设。
> 任何"只有一个实例"的程序（浏览器、IDE、笔记软件）都必须处理这一条，否则升级体验会断裂。

## 十二、三层 schema：别混为一谈

"schema" 在这个项目里有三个完全不同的东西，混着说会误判进度：

| # | 名称 | 描述什么 | 载体 | 当前状态 | 由谁决定 |
|---|---|---|---|---|---|
| S1 | **抽取 schema** | LLM 从图片里能吐出哪些字段 | prompt 的 JSON 结构 + `ExtractedFact` | **已迭代 1 轮**（5→7 个事实字段），待探针定稿 | 真实样本 |
| S2 | **规则配置 schema** | "细则"能被表达成什么结构 | `configs/**.yaml` + JSON Schema + 校验器 | **只有德育样例，schema 本身没抽出来** | 第二份学院细则 |
| S3 | **持久化 schema** | 数据落库长什么样 | H2 4 张表 | 已给 DDL，**建议不用**（F1） | 需求，现在不需要 |

**关键：S1 和 S2 都不能拍脑袋定，它们由输入数据决定。**

- S1 由"证书长什么样"决定 —— 2026-10-26 那两份样本，直接让 `date` 裂成了 `date / period_start / period_end`
- S2 由"细则长什么样"决定 —— 德育已经能表达，但**智育竞赛要两次查表**（先查目录定级、再查矩阵算分），**体育是公式换算**（体测分数→得分），这两类还没验证过

所以"确定 schema"的正确形态是：**先喂数据，看 schema 撑不撑得住**，而不是先写一份再找数据塞进去。

## 十三、下一步的真实顺序（由依赖决定，不是由重要性决定）

```
① 跑探针（20 分钟）                  → S1 定稿：知道哪些字段模型能稳定给出
        ↓
② 补齐规则内容（德育已有，智育缺）    → 需先把竞赛目录 PDF 结构化
        ↓
③ 抽出 S2 的 schema + 校验器          → 出口：别人能照它写新学院的 YAML
        ↓
④ 拿第二份学院细则验证 S2 表达力      → 配置化假设成立与否
```

**为什么不能跳过 ①**：S2 的规则条目要**指向** S1 的字段。比如"命中竞赛目录 + 国家级 + 一等奖 → 20 分"，这些条件依赖抽出来的 `level_hint` / `achievement`。S1 还在动，S2 写出来一定返工。

**为什么 ② 是隐藏工作量**：三种细则形态对 schema 的要求完全不同——

| 维度 | 规则形态 | 对 schema 的要求 |
|---|---|---|
| 德育 | 查表（级别 × 等级矩阵） | 二维矩阵 + 冲突合并 |
| 智育 | **两次查表**（竞赛名→目录定级→矩阵算分） | 需要外挂目录 + 模糊匹配 + 候选 |
| 体育 | **公式换算**（体测分数 → 得分） | 需要数值映射/线性插值，不是查表 |

**只按德育设计 schema，等智育进来就会推翻它。** 这是 §12 说"S2 由细则决定"的具体含义。

> 结论：下一件事是**跑探针**，不是写 schema。但 §11 那 6 条可以现在就勾——勾完就能一边跑探针一边开始动代码。
